# Authentication

Spring Security provides authorization code OAuth 2.0 and OIDC for public client `world-web`. Its registered callback and logout return URI are configuration values. The authorization request must contain PKCE S256; scopes are `openid profile world`. Discovery is `/.well-known/openid-configuration`; use its advertised authorization, token, JWKS, UserInfo and `end_session_endpoint` addresses. Dynamic client registration is disabled.

Clients should send unpredictable `state` and OIDC `nonce` values. The ID token echoes the requested nonce; the client verifies both values when completing login. A code can be exchanged once, with the original S256 verifier and registered redirect URI. PKCE validation runs before the authorization endpoint can create a code or redirect to login.

The backend `/login` page keeps CSRF protection and uses WebCrypto SHA-256 over UTF-8 password bytes before posting `passwordDigest`. The raw password field has no form name. Login requires a secure browser context (HTTPS or localhost); unsupported hashing disables submission. Accepted digests are exactly 64 lowercase hexadecimal characters, with no raw-password fallback. SQLite stores BCrypt of the digest with credential scheme `sha256-v1`.

Anonymous `POST /api/v1/auth/register` accepts `{username,email,passwordDigest}` and returns 201 `{id,username,email}`. Usernames contain 3–32 ASCII letters, digits, underscores or hyphens. Email is trimmed and lowercased before a unique insert; duplicate username or email returns 409 and invalid fields return 400. Registration does not create a session or token; clients then use the OIDC login flow.

The demo username defaults to `demo`; the first startup requires `WORLD_DEMO_PASSWORD` from the local environment or `.env`. Existing digest accounts preserve their ID and hash. A migrated `raw-bcrypt` demo account upgrades only when the configured raw password matches its stored BCrypt hash; otherwise startup fails without changing the credential. Other legacy accounts remain disabled until a separate recovery process is implemented. The local `.env` and `data/` are ignored by Git.

Access tokens last ten minutes, with users.id in `sub`, `world-api` in `aud` and `token_use=access_token`. Protected `/api/v1/**` endpoints accept bearer tokens only, check signature, issuer, expiration and audience, and require `SCOPE_world`; anonymous registration is the exception. ID tokens and login cookies cannot authorize protected APIs. `/api/v1/me` returns `{id,username,email}` for the signed-in user; migrated/demo email may be null.

API authentication failures return 401 and missing `world` scope returns 403, both as `application/problem+json` with a `WWW-Authenticate` header. Error details do not include bearer values or JWT decoder errors. CORS uses the configured exact origin, permits Authorization/Content-Type headers and GET/POST/PUT/PATCH/DELETE/OPTIONS, and does not allow credentialed requests. Browser form login remains a server navigation protected by CSRF.

Private RSA JWK material persists at `WORLD_AUTH_KEY_PATH` (default `./data/signing-key.json`), so restart preserves JWT verification. Protect this file with filesystem permissions and backups; changing it invalidates outstanding tokens. OAuth grants and login sessions are in memory, and disappear on restart. No refresh token is issued.

OIDC logout uses the advertised `/connect/logout` endpoint with ID-token hint and registered post-logout URI. The caller clears its local tokens. Logout ends the server login session; already issued bearer JWTs remain valid until their ten-minute expiration. Production deployments must configure HTTPS issuer, callback, allowed CORS origin, logout return URI and private-key directory permissions.

Login and registration share bounded per-process throttling of 30 requests per minute for each remote address and endpoint (4096 active address/endpoint slots, fail closed when full). Exhaustion returns 429 with Retry-After. `WORLD_AUTH_REQUIRE_HTTPS` can reject insecure authentication requests, allowing direct loopback development only with `WORLD_AUTH_ALLOW_LOCAL_HTTP`. These checks use the connection address and secure flag; proxy forwarded headers are not trusted.
