# Photo media

JWT subject identifies the event owner. `POST /api/v1/events/{eventId}/photos/presign` validates the event, photographer, JPEG/PNG/WebP filename, declared bytes and optional GPS/time, reserves the next import order (including pending rows), then returns a five-minute PUT URL and required headers. The browser uploads directly to RustFS. Responses use UTC epoch milliseconds.

`POST /api/v1/events/{eventId}/photos/{photoId}/confirm` checks the staging object's content type and exact positive declared size (20 MiB by default), copies it conditionally using the observed ETag to a separate random final key, and verifies the final HEAD including the COPY result ETag. Only then does a short SQLite transaction assign an island and publish READY. Network work occurs outside the transaction. Concurrent confirms are serialized per photo in the single application process; READY confirmation is idempotent even if storage becomes unavailable. A PENDING intent at or beyond expiry returns 410.

`POST /api/v1/events/{eventId}/photos/download-urls` accepts 1–100 photo IDs. All must belong to the event and be READY before any URL is signed. URLs last fifteen minutes by default and are never persisted. Upload URLs target staging only, so replaying a still-valid PUT cannot overwrite a published final photo. Unknown/foreign/pending photos return 404; invalid upload metadata returns 400; storage failures return a safe 503 without exposing SDK details.

`StorageProperties.publicEndpoint` is the externally reachable S3 endpoint used by the SDK presigner, while `endpoint` is the internal HEAD/COPY endpoint. Both clients use path style and the configured bucket/region. Browser PUT clients must send the response `headers` map exactly; Host is browser managed. Presigning disables optional SDK checksum requirements for RustFS/browser compatibility. Deployment must configure bucket CORS and a lifecycle rule matching staging paths to remove abandoned upload objects; no cleanup worker is provided. Validation checks object metadata, not image decoding or file magic. This service assumes one application process owns the SQLite writer; a distributed deployment needs a durable confirmation claim.

Verification: `MediaServiceTests` uses temporary SQLite databases and mocks remote storage for ownership, metadata, transaction boundaries, retry, expiry, idempotence and concurrent confirmation. `RustFsStorageGatewayTests` exercises real SDK SigV4 URLs and internal HEAD/COPY requests against a local HTTP stub. Live RustFS/CORS validation remains a deployment check.
